# Auto Stories — Spec · Phase 2: Get it onto Instagram

Phase 2 takes the finished story from [Phase 1](../phase-1/spec.md) and gets it posted. Built only once Phase 1 produces a story worth posting.

## Goal
Move a finished story from the app onto the user's Instagram Story with the least friction, without needing Instagram API approval. Instagram gives an app **no one-tap way to post all cards at once** (Meta's SDK takes one card per call; Select Multiple is Instagram's own UI, which an outside app can't pre-load) — so the story posts **one card at a time**. Phase 2 makes finishing feel effortless: **web-first** (no install required), a **resumable "burn-down" flow** tuned against drop-off with real completion research, and the **native app as the promoted way to post** card-by-card. (Full reasoning: [decisions Chapter 7](../decisions.md#chapter-7--phase-2-getting-the-story-onto-instagram).)

## Scope

**In scope:**
- **Longer stories — up to 30 photos, generated async.** Raise the pick from 10 to 30 so the user hands over a full camera-roll dump and the AI *selects* the best frames, not just orders a pre-trimmed set (the value in [approach 2.4](../decisions.md#24-how-many-photos-can-the-user-bring-in)). Generation runs as a background job so it can't hit Render's request timeout: `POST /api/v1/generate` returns a `jobId` immediately, an in-memory queue with one worker runs the model call, and the finished frames are pushed back over **Server-Sent Events**. All 30 photos go to the model in one call — no per-photo pipeline (the existing proxy size already fits the request body cap). (Reasoning: [decisions.md Chapter 6](../decisions.md#chapter-6--phase-2-longer-stories-without-timing-out).)
- **Try it free on the web, no install.** The browser does the whole build with no app: generate → refine → **download the images** (and on mobile web, save + **Select Multiple** posts with no app). Install is never forced; the app is pitched right *after* the user has seen their finished story. Web stays open because a hard install gate sheds most users (Google: **69%** abandoned an install interstitial; **+17%** mobile-web actives when it was removed). (Reasoning: [decisions 7.8](../decisions.md#78-web-tries-it-free-through-download-the-native-app-is-the-promoted-way-to-post).)
- **Make finishing feel effortless — a resumable "burn-down" finalize flow (in the app).** One screen: an endowed-progress meter that opens with **"Story built ✓"** already filled (never "0 of N"); the cards listed with the **single active card as the only anchor**; **goal-gradient** copy as the end nears ("2 left"); a **completion state that leads straight into the music suggestions**. Progress **persists locally and resumes on the same device** (no server store), so an interruption never restarts. Ordering: **hook card first, a strong card last**. The web path shares the framing but is one trip (Select Multiple). Grounded in completion research (endowed progress lifted a comparable rate **19%→34%**; save-and-resume cut abandonment **~25%**). (Reasoning: [decisions 7.7](../decisions.md#77-the-finalize-flow-app-path-a-resumable-burn-down-tuned-for-completion).)
- **The native app (Capacitor) — the promoted way to post.** Wrap the existing Angular app in an iOS/Android shell (whole UI reused) to reach Meta's **Sharing to Stories** SDK. Each card is two layers: a **background photo** (9:16) + the **caption as a movable/resizable sticker** (a full-canvas transparent PNG placed where the user set it in Phase 1). Tap "Add to story" → Instagram opens with the card **pre-loaded**; on return the app uses **optimistic detection** — mark Shared, advance, one-tap **Undo** — so the 5–7 hand-offs feel like a guided burn-down, not repeated taps. One custom plugin (iOS pasteboard + `instagram-stories://share`; Android `ADD_TO_STORY` intent) + a registered Facebook App ID. (Reasoning: [decisions 7.2–7.3](../decisions.md#72-delivery-per-card-sdk-deep-link-background-image--caption-sticker), [7.8](../decisions.md#78-web-tries-it-free-through-download-the-native-app-is-the-promoted-way-to-post).)
- **Readable captions by default — AI auto-styling (metadata only).** The generator returns a **readable, vibe-matched caption treatment per card** — contrast-safe color, an optional scrim, a font from a small curated set — as **styling metadata** on the same JSON it already returns; the client/app composites it **on-device** from the full-res original. No server-side rendering and no image bucket: it rides the **existing metadata channel**, so the architecture doesn't change. Manual fine-tuning still happens in Instagram. (Reasoning: [decisions 7.10](../decisions.md#710-in-app-customization-is-out-readability-auto-styling-is-in-phase-2-as-metadata-only).)
- **Desktop → phone: a "get the app" CTA, not a story transfer.** Once the web user has a finished story (images downloadable), desktop shows a QR / mobile a button — **"Post straight to Instagram — get the app"** — that opens the Play Store / TestFlight. The story does **not** transfer; the user builds it fresh in the app, where their photos already live. **No server storage, no persistence, no full-res re-upload** — that subsystem is out of scope this stage. On mobile web the manual Select-Multiple post still works with no app. Revisit persistence-backed continuity with accounts (Phase 3). (Reasoning: [decisions 7.5](../decisions.md#75-the-qr-is-a-get-the-app-cta-not-a-story-transfer-bridge-no-persistence).)
- **Early distribution** — **Google Play first, free** (data-gathering); Apple later. Before store listings exist, install is **TestFlight** on iOS (public link, lightweight beta review, $99/yr account, 90-day builds; no free sideloading) and a **direct APK / Play open testing** on Android (near-zero gate). The free web path (7.8) bridges anyone who won't complete an install. (Reasoning: [decisions 7.6](../decisions.md#76-distribution-before-the-stores-testflight-ios--apk--play-testing-android), [7.9](../decisions.md#79-rollout-google-play-first-free-to-learn-before-investing-in-ios).)
- **Music suggestions** — the app reads the story's vibe and tells the user what to search for in Instagram's music tab (mood, genre, example tracks), so adding the Music sticker per card is effortless. Just generated text — Instagram's music is licensed and addable only inside Instagram. (Reasoning: [decisions 7.4](../decisions.md#74-music-is-added-in-instagram-guided-by-suggestions--never-baked-by-us).)
- **Don't lose work on refresh** — persist a local draft (story state + downscaled proxies) to **IndexedDB**, restored on next open in the same browser, plus a `beforeunload` warning. This same local state powers the **resumable finalize flow** (7.7): which cards are posted survives leaving for Instagram and returning. Stabilizing, so it lands in Phase 2 rather than the Phase 1 core (see approach 4.6). Cross-device sync needs accounts → Phase 3.

**Out of scope:**
- **Automatic / direct posting via the Instagram API** — needs a Business account + Facebook Page + Meta App Review; too heavy. Per-card hand-off instead.
- **A click bot that scripts Instagram** — automating a personal account breaks Instagram's Terms, risks the account being locked/banned, and needs harvested credentials. (Reasoning: [decisions 7.1](../decisions.md#71-there-is-no-one-tap-post-all-my-cards--instagram-takes-one-card-at-a-time).)
- **One-tap "post all cards at once"** — Instagram accepts one card per SDK call and can't be pre-loaded via Select Multiple; not achievable by any app.
- **An in-app customization editor** (manual colours / fonts / stickers UI) and any **server-rendered or bucket-backed** styling — redundant with Instagram's editor, and anything that would change the architecture is deferred to a later phase (only metadata-channel auto-styling is in Phase 2). (Reasoning: [decisions 7.10](../decisions.md#710-in-app-customization-is-out-readability-auto-styling-is-in-phase-2-as-metadata-only).)
- **Editing the caption's words inside Instagram** — the caption is handed over as a sticker image (movable, not re-typeable); re-wording is done in our app.
- Music (audio), animated GIFs, interaction stickers — the user adds these in Instagram.

## System architecture

![Phase 2 system architecture: Angular web app → NestJS backend (in-memory queue) → multimodal AI model (vision + text); POST enqueues a job, the story is pushed back over SSE](diagrams/system-architecture.png)

Generation is a background job so a 30-photo run can't hit Render's request timeout. `POST /api/v1/generate` enqueues the work in an **in-memory queue** (one job at a time — the free tier is a single container) and the finished story is pushed back over **Server-Sent Events**. The worker makes **one model call** for all N photos (up to 30) — `gemini-flash-latest` accepts far more than 30 images per request, so no per-photo pipeline is needed; the model selects 5–7, orders (EXIF capture time as a soft hint), and captions in a single pass. (Full reasoning: [decisions Chapter 6](../decisions.md#chapter-6--phase-2-longer-stories-without-timing-out).)

The diagram covers **generation**; it predates the Phase 2 delivery decisions and does not yet show the **Capacitor native shell** or the **Sharing-to-Stories SDK hand-off** (Chapter 7). No server-side story storage is used — the desktop→phone QR is a "get the app" CTA, not a data bridge (7.5). To be redrawn.

## Why hand-off, not API
Publishing programmatically requires a Business/Creator account, a linked Facebook Page, and Meta App Review (weeks). Personal accounts are excluded. The per-card hand-off needs none of that and keeps the user in control of the final post. (Full reasoning in `decisions.md`.)
