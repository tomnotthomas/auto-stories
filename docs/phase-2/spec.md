# Auto Stories — Spec · Phase 2: Get it onto Instagram

Phase 2 takes the finished story from [Phase 1](../phase-1/spec.md) and gets it posted. Built only once Phase 1 produces a story worth posting.

## Goal
Move a finished story from the app onto the user's Instagram Story with the least friction, without needing Instagram API approval. Instagram gives an app **no one-tap way to post all cards at once** (Meta's SDK takes one card per call; Select Multiple is Instagram's own UI, which an outside app can't pre-load) — so the story posts **one card at a time**. **Phase 2 is web-only:** the browser builds the story and the user hands it off to Instagram themselves — download the frames, or on mobile web save + **Select Multiple** — plus deterministic **auto-styling** for readable captions. The **native app** (per-card Sharing-to-Stories SDK hand-off, "burn-down" finalize UX, QR-to-app, distribution) is **deferred to [Phase 3](../phase-3/spec.md)**, gated on Phase 2 web evidence ([decisions 7.11](../decisions.md#711-phase-2-ships-web-only-native-app-and-per-card-hand-off-move-to-phase-3)). The reasoning for the native path is already worked out in [decisions Chapter 7](../decisions.md#chapter-7--phase-2-getting-the-story-onto-instagram); it just moves phases.

## Scope

**In scope:**
- **Longer stories — up to 30 photos, generated async.** Raise the pick from 10 to 30 so the user hands over a full camera-roll dump and the AI *selects* the best frames, not just orders a pre-trimmed set (the value in [approach 2.4](../decisions.md#24-how-many-photos-can-the-user-bring-in)). Generation runs as a background job so it can't hit Render's request timeout: `POST /api/v1/generate` returns a `jobId` immediately, an in-memory queue with one worker runs the model call, and the finished frames are pushed back over **Server-Sent Events**. All 30 photos go to the model in one call — no per-photo pipeline (the existing proxy size already fits the request body cap). (Reasoning: [decisions.md Chapter 6](../decisions.md#chapter-6--phase-2-longer-stories-without-timing-out).)
- **Web finalize path — the way to post in Phase 2.** The browser renders each card into a flat **1080×1920** image (photo + placed caption). Desktop **downloads** them; mobile web **saves via Web Share**; the user then posts through Instagram's **Select Multiple** (all cards in one trip). No install, no SDK — human-in-the-loop hand-off by design. **Spike first:** iOS Safari multi-image save-to-Photos and Android Web Share multi-file both vary by version — validate the real friction before calling it done.
- **Readable captions by default — auto-styling (metadata only).** **Contrast + scrim are computed deterministically on-device** — sample the luminance under the caption's box on the full-res original, pick black/white text and add a scrim below a WCAG-ish threshold. A pure, testable function, **not** model-generated (the model only ever saw the downscaled proxy). The model optionally contributes only the **subjective font/vibe** as **styling metadata** on the JSON it already returns; **recomputed when the user drags the caption** (placement is movable, Phase 1). Rides the existing metadata channel — no server rendering, no image bucket, no architecture change. Font bundling/licensing to be settled before shipping model-chosen fonts. (Reasoning: [decisions 7.10](../decisions.md#710-in-app-customization-is-out-readability-auto-styling-is-in-phase-2-as-metadata-only).)
- **Don't lose work on refresh** — persist a local draft (story state + downscaled proxies) to **IndexedDB**, restored on next open in the same browser, plus a `beforeunload` warning. Stabilizing, so it lands in Phase 2 rather than the Phase 1 core (see approach 4.6). Cross-device sync needs accounts → Phase 3.

**Out of scope (Phase 2):**
- **Native app + per-card Instagram hand-off → [Phase 3](../phase-3/spec.md).** The Capacitor shell, the Sharing-to-Stories SDK per-card deep link (background photo + movable caption sticker), and the resumable **"burn-down"** finalize UX (endowed progress, optimistic-mark + Undo, goal-gradient) are deferred. Native is a large build — two native codebases, a Facebook App ID, two store accounts — that makes multi-card *higher*-friction than the web Select-Multiple trip, so it's **gated on Phase 2 evidence** that the web hand-off actually loses users. Reasoning kept in [decisions 7.2–7.3](../decisions.md#72-delivery-per-card-sdk-deep-link-background-image--caption-sticker), [7.7](../decisions.md#77-the-finalize-flow-app-path-a-resumable-burn-down-tuned-for-completion), [7.11](../decisions.md#711-phase-2-ships-web-only-native-app-and-per-card-hand-off-move-to-phase-3).
- **QR "get the app" CTA + app distribution (Google Play first) → Phase 3** — they only matter once the native app exists. (Reasoning: [decisions 7.5](../decisions.md#75-the-qr-is-a-get-the-app-cta-not-a-story-transfer-bridge-no-persistence), [7.6](../decisions.md#76-distribution-before-the-stores-testflight-ios--apk--play-testing-android), [7.9](../decisions.md#79-rollout-google-play-first-free-to-learn-before-investing-in-ios).)
- **Automatic / direct posting via the Instagram API** — needs a Business account + Facebook Page + Meta App Review; too heavy.
- **A click bot that scripts Instagram** — breaks Instagram's Terms, risks account bans, needs harvested credentials. (Reasoning: [decisions 7.1](../decisions.md#71-there-is-no-one-tap-post-all-my-cards--instagram-takes-one-card-at-a-time).)
- **One-tap "post all cards at once"** — Instagram accepts one card per SDK call and can't be pre-loaded via Select Multiple; not achievable by any app.
- **An in-app customization editor** (manual colours / fonts / stickers UI) and any **server-rendered or bucket-backed** styling — redundant with Instagram's editor; only metadata-channel auto-styling is in Phase 2. (Reasoning: [decisions 7.10](../decisions.md#710-in-app-customization-is-out-readability-auto-styling-is-in-phase-2-as-metadata-only).)
- **Music suggestions** — deferred; cut from the current Phase 2 build (2026-07-31). (Reasoning: [decisions 7.4](../decisions.md#74-music-is-added-in-instagram-guided-by-suggestions--never-baked-by-us).)
- Music (audio), animated GIFs, interaction stickers — the user adds these in Instagram.

## System architecture

![Phase 2 system architecture: Angular web app → NestJS backend (in-memory queue) → multimodal AI model (vision + text); POST enqueues a job, the story is pushed back over SSE](diagrams/system-architecture.png)

Generation is a background job so a 30-photo run can't hit Render's request timeout. `POST /api/v1/generate` enqueues the work in an **in-memory queue** (one job at a time — the free tier is a single container) and the finished story is pushed back over **Server-Sent Events**. The worker makes **one model call** for all N photos (up to 30) — `gemini-flash-latest` accepts far more than 30 images per request, so no per-photo pipeline is needed; the model selects 5–7, orders (EXIF capture time as a soft hint), and captions in a single pass. (Full reasoning: [decisions Chapter 6](../decisions.md#chapter-6--phase-2-longer-stories-without-timing-out).)

The diagram covers **generation**. Phase 2 delivery is **web-only**: the browser renders flat frames the user downloads and posts via Instagram's Select Multiple, and auto-styling is computed on-device. **No native shell and no server-side story storage in Phase 2.** (The native Sharing-to-Stories path is [Phase 3](../phase-3/spec.md), Chapter 7 / 7.11.) The frame-render + hand-off box isn't drawn yet — to be redrawn.

## Why hand-off, not API
Publishing programmatically requires a Business/Creator account, a linked Facebook Page, and Meta App Review (weeks). Personal accounts are excluded. The per-card hand-off needs none of that and keeps the user in control of the final post. (Full reasoning in `decisions.md`.)
