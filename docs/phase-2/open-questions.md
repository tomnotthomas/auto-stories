# Open Questions — Phase 2: Get it onto Instagram

1. ~~**Do we put music in the stories?**~~ **Resolved:** music-as-audio is out of scope (Instagram-licensed, needs video + licensing). Instead the app generates **music suggestions** (mood/genre/search terms) so the user adds it easily in Instagram.

2. ~~**Does one Gemini call handle 30 images well, or do we need a pipeline?**~~ **Resolved: one call.** `gemini-flash-latest` accepts up to 3,600 images per request for image input (Google docs, checked 2026-07-27), so 30 is well within limits; the only binding constraint is the 50mb request body, which 30 downscaled proxies fit ([decisions 6.4](../decisions.md#64-photo-proxy-size-at-30-photos--no-change-needed)). The describe-then-decide pipeline is **dropped** ([decisions 6.5](../decisions.md#65-stories-up-to-30-photos-stay-a-single-call--pipeline-dropped)); it's the recorded fallback only if the single-call eval later shows quality degrading at 20–30 photos.

3. ~~**How does the finished story actually get onto Instagram — can one button post it?**~~ **Resolved:** No one-tap "post all cards" exists — Instagram takes **one card per SDK call** and Select Multiple can't be pre-loaded by an outside app ([decisions 7.1](../decisions.md#71-there-is-no-one-tap-post-all-my-cards--instagram-takes-one-card-at-a-time)). Delivery is the **per-card Sharing-to-Stories SDK deep link** — background photo + caption as a movable sticker — via a native app ([7.2](../decisions.md#72-delivery-per-card-sdk-deep-link-background-image--caption-sticker), [7.3](../decisions.md#73-package-as-a-native-app-via-capacitor)). Auto-post via API and a click bot were both rejected (7.1). **Refined (7.8):** the app is the *promoted* way to post, not the required path — posting is **web-first** (browser builds + downloads; mobile-web Select Multiple posts), and the desktop→phone QR is a **"get the app" CTA**, not a story transfer ([7.5](../decisions.md#75-the-qr-is-a-get-the-app-cta-not-a-story-transfer-bridge-no-persistence)).

4. ~~**Can we put music on the story?**~~ **Resolved:** Not baked by us — Instagram's music is licensed and addable only via the in-app Music sticker; the SDK has no audio field ([decisions 7.4](../decisions.md#74-music-is-added-in-instagram-guided-by-suggestions--never-baked-by-us)). The user adds it **per card in Instagram**, guided by our search-term suggestions (same as Q1's resolution).

5. ~~**How do we mitigate the per-card ping-pong so users finish the story?**~~ **Resolved (design):** a **resumable "burn-down" finalize flow** ([decisions 7.7](../decisions.md#77-the-finalize-flow-app-path-a-resumable-burn-down-tuned-for-completion)) — endowed-progress meter that never starts at zero, the active card as the only anchor, **optimistic return-detection + Undo** (no manual "mark as posted"), goal-gradient copy near the end, resume on the same device, completion → music. Ordering: hook first, strong card last. Grounded in completion research (Q8). **Still to validate on device:** typical card count, whether the rhythm feels good, and real drop-off by card position.

6. ~~**Do we persist the desktop story so the phone can continue it?**~~ **Resolved: no persistence this stage.** No blob storage, no server-held story, no full-res re-upload — too much work now. The desktop→phone QR is a **"get the app" CTA**, not a data bridge; the user builds fresh in the app ([decisions 7.5](../decisions.md#75-the-qr-is-a-get-the-app-cta-not-a-story-transfer-bridge-no-persistence)). **Accepted limitation:** a desktop-built story isn't continued on the phone. Revisit persistence-backed continuity with accounts (Phase 3).

7. ~~**How do people install the app before it's in the stores, and what if they won't install?**~~ **Resolved:** iOS has no free sideloading → **TestFlight** (public link, beta review, $99/yr, 90-day builds); Android → **direct APK / Play open testing** ([decisions 7.6](../decisions.md#76-distribution-before-the-stores-testflight-ios--apk--play-testing-android)). **Google Play first** ([7.9](../decisions.md#79-rollout-google-play-first-free-to-learn-before-investing-in-ios)). The **browser is the free no-install on-ramp** (build + download; mobile-web Select Multiple posts), and the **native app is the promoted way to post** ([7.8](../decisions.md#78-web-tries-it-free-through-download-the-native-app-is-the-promoted-way-to-post)); install is offered, never forced. **Open trigger:** watch conversion by path (web vs app) to tune how hard to pitch the app once the stores lower the iOS install cost.

8. ~~**What's the best-practice, data-backed UX for finishing the story?**~~ **Resolved:** two research streams (completion/drop-off science + hand-off case studies) drive [decisions 7.7](../decisions.md#77-the-finalize-flow-app-path-a-resumable-burn-down-tuned-for-completion), [7.8](../decisions.md#78-web-tries-it-free-through-download-the-native-app-is-the-promoted-way-to-post), and the conversion-CTA framing in [7.5](../decisions.md#75-the-qr-is-a-get-the-app-cta-not-a-story-transfer-bridge-no-persistence). Key primary sources: goal-gradient (Kivetz et al. 2006, JMR), endowed progress (Nunes & Drèze 2006, JCR: 19%→34%), peak-end (Kahneman et al. 1993), Baymard checkout-friction benchmarks, Google's app-install interstitial case study (69% abandon / +17% web actives), Apple TestFlight docs, and hand-off patterns from Later/Buffer/Planoly + WhatsApp/Steam/Open-Banking QR. Vendor figures (Chameleon 3-step≈72% vs 7-step≈16%, Duolingo streaks, QR stats) are directional, not audited.

9. **Phase 3 (native) — "finish later" nudge + optimistic-mark edges.** The burn-down flow is Phase 3 now ([7.11](../decisions.md#711-phase-2-ships-web-only-native-app-and-per-card-hand-off-move-to-phase-3)). (a) Re-engagement channel if a user leaves mid-story: web push, SMS (no install), or in-app only? Loss-framed. (b) **Resolved (design):** the mis-mark risk is handled by a **persistent per-card `Shared · Undo`** (kept until the user leaves the finalize screen) fired on the Capacitor `resume` signal, re-tap idempotent — since Instagram gives no post/cancel callback ([7.7](../decisions.md#77-the-finalize-flow-app-path-a-resumable-burn-down-tuned-for-completion); eng review 2026-07-31). Still to validate on device: `resume`-event reliability on iOS.

10. **Open — how far to push auto-styling (metadata-only).** Auto-styling is in Phase 2 as **styling metadata**, no architecture change; **contrast + scrim are computed deterministically client-side** (not model-generated), the model only does subjective font/vibe ([decisions 7.10](../decisions.md#710-in-app-customization-is-out-readability-auto-styling-is-in-phase-2-as-metadata-only)). **Validation gate:** review 5–10 real generated stories and measure how many captions are genuinely hard to read against their photo. Readability defect rate → auto-contrast is justified; repeated "different look" requests → consider a swap-treatment option (still metadata). Anything needing server-side rendering / a bucket is deferred. **Let the defect rate size the feature.**

11. **Open — the gate that justifies building the native app (Phase 3).** Phase 2 is web-only; native is built only once data shows the web hand-off loses users ([decisions 7.11](../decisions.md#711-phase-2-ships-web-only-native-app-and-per-card-hand-off-move-to-phase-3)). **Metric to instrument in Phase 2:** the share of users who reach "download / save frames" but don't complete the Instagram Select-Multiple post (a lightweight "did you post?" ping), plus the desktop→mobile drop. **Threshold to set:** what abandonment rate makes two native codebases + a Meta App ID + store accounts worth it.
